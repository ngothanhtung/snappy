# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Snappy is a macOS menu-bar agent app (no Dock icon, `LSUIElement`) that snaps the
focused window to halves/thirds and moves it between displays via global keyboard
shortcuts. Built with Swift Package Manager (not an Xcode project), targeting
macOS 14+. Also supports **Region Capture** — drag-select a screen region, then
annotate it with arrows/rectangles/circles/text before copying or saving as PNG.

## Commands

```bash
swift test                          # run all SnappyCore unit tests
swift test --filter LayoutCalculatorTests          # one test class
swift test --filter LayoutCalculatorTests/leftHalf # one test method
swift build                         # debug build (compile check)
./Scripts/bundle.sh                 # release build + assemble Snappy.app
open ./Snappy.app                   # launch the assembled app
```

Tests only cover `SnappyCore` — the `Snappy` app target depends on AppKit /
Accessibility APIs and is not unit tested. After changing core logic, `swift test`
is the fast feedback loop; to verify actual window behavior you must `bundle.sh`
and launch (see Accessibility note below).

## Architecture

Two SPM targets, split by testability:

- **`SnappyCore`** — pure, dependency-free, fully unit-tested geometry. No AppKit,
  no side effects. Everything here is `static` functions on enums:
  - `LayoutCalculator.frame(for:in:)` — the layout math (halves/thirds → `CGRect`)
  - `Geometry.flipY` — converts between coordinate systems (see gotcha below)
  - `DisplayMapper` — maps a window proportionally onto another display
  - `DisplayOrdering` — picks prev/next display by screen position
- **`Snappy`** — the app layer (AppKit + Accessibility + KeyboardShortcuts dep).
  Keep this thin; push any non-trivial geometry down into `SnappyCore` so it can
  be tested.

Control flow: `Main` (sets `.accessory` policy) → `AppDelegate` installs
`StatusMenuController` (the status item opens `StatusPanelController`: a
four-column, menu-like non-activating panel — Snap (+ move to next/previous
display) · Displays · Capture · Maintenance + Mini Display/Settings/About/Quit; non-activating so the user's
app stays frontmost for window snapping), calls `HotkeyManager.registerAll()`, and requests
Accessibility. A shortcut or menu item produces an `AppAction`, which
`WindowManager.perform` dispatches: it builds a `Context` (focused window +
its screen via `WindowEngine`/`ScreenProvider`), computes the target frame with
`SnappyCore`, and writes it back through `WindowEngine.setFrame`.

### Single source of truth for actions

`ShortcutNames.swift` is the one place defining every action. `AppAction`,
`ActionBinding`, and `Bindings.all` drive hotkey registration
(`HotkeyManager`), the status menu (`StatusMenuController`), and the settings UI
(`SettingsView`). To add or change a shortcut/layout, edit this file (and add the
`WindowLayout` case + calculator branch in `SnappyCore` if it's a new layout) —
the rest wires up automatically.

### Coordinate systems (the central subtlety)

AppKit uses a global origin at the **bottom-left** of the primary screen (y up);
the Accessibility API uses **top-left** (y down). `WindowManager` reads frames in
AX coords, flips with `Geometry.flipY(_:primaryHeight:)` where `primaryHeight` is
`NSScreen.screens.first?.frame.height`, does all layout math in AX/top-left space,
then writes AX coords back. The flip is its own symmetric transform. When touching
window placement, be explicit about which space a `CGRect` is in.

`WindowEngine.setFrame` sets position → size → position again on purpose: some apps
clamp the new position against the old size on the first pass.

## Accessibility permission + code signing (critical for testing the real app)

macOS ties the Accessibility (TCC) grant to the app's **code signature**.
`bundle.sh` defaults to ad-hoc signing (`codesign --sign -`), which produces a new
signature every rebuild, **silently invalidating** the previous grant — window
snapping then fails quietly. Two ways to deal with it:

- Quick: after each ad-hoc rebuild, remove and re-add Snappy in **System Settings
  → Privacy & Security → Accessibility**.
- Stable: create a self-signed Code Signing cert in Keychain Access, then
  `export SNAPPY_SIGN_IDENTITY="Snappy Self-Signed"` before `bundle.sh`. The grant
  survives rebuilds. (See README.md for full steps.)

`WindowManager.perform` and `AppDelegate` go through `AccessibilityPermission`,
which surfaces guidance instead of failing silently when untrusted.

## Region Capture + Annotation pipeline

User-facing flow: trigger via shortcut or menu → `RegionCaptureController` →
borderless `RegionOverlayWindow` (Phase 1 drag-select, Phase 2 resize via 8
handles + Cancel/Capture pill, ESC to cancel) → `DispatchQueue.main.asyncAfter
0.15s` (let overlay vanish from compositor) → `SCScreenshotManager.captureImage`
→ crop to selection → hand `NSImage` to `AnnotationEditorController` →
borderless-ish editor window with hand-laid toolbar (segmented tool picker, 5
`ColorSwatchButton`s, `NSStepper` width, Undo/Copy/Save…) above an
`AnnotationCanvasView` that draws the image + per-tool annotations and exports
via `NSPasteboard` or `NSSavePanel` PNG.

All NSLogs emitted by these components are prefixed `Snappy:` — filter process
`Snappy` in Console.app to debug capture/annotation live (`CGWindowListCreateImage
returned nil` is the smoking gun for the API obsolescence below; `ScreenCaptureKit
cgImage WxH` / `cropped CGImage WxH` confirm the new pipeline ran).

### Cloud upload (Google Drive / GitHub)

The annotation editor's Copy/Save toolbar also offers "Upload to Drive" / "Upload
to GitHub", handled in `AnnotationEditorController` via `GoogleDriveClient.shared`
and `GitHubUploader.shared` (both singletons, both check `.isConfigured` before
attempting an upload). Settings for both live in `SettingsView`, backed by
`@AppStorage` for non-secret config (client ID, repo/branch/folder) and
`KeychainStore` (a thin Keychain wrapper) for secrets (tokens, client secret).

- `GoogleDriveClient` does OAuth2 with PKCE: `authorize()` opens the system
  browser, spins up a local loopback listener (`RedirectCatcher`, built on
  `NWConnection`, not `URLSession`) to catch the redirect, exchanges the code for
  tokens, and refreshes silently via `validAccessToken()` before each upload.
  Uploaded files are created inside a `snappy` folder in the user's Drive.
- `GitHubUploader` is simpler: a user-supplied personal access token (PAT) is
  used to commit the PNG straight to a configured repo/branch/folder via the
  Contents API.

Both are best-effort, opt-in features — they no-op instead of erroring if
unconfigured, so this doesn't gate the core capture/annotate flow.

## Screen-capture APIs — DO NOT use the legacy ones

`CGWindowListCreateImage` and `CGDisplayCreateImage(_:rect:)` are both
`SCREEN_CAPTURE_OBSOLETE(10.6,14.4,15.0)` — they still compile under the
`macOS(.v14)` SPM deployment target but **return nil at runtime on macOS 15+**.
Use `ScreenCaptureKit`'s `SCScreenshotManager.captureImage(contentFilter:
configuration:completionHandler:)` instead (macOS 14.0+). If you need to
target a sub-rect of a display, capture the full display first then
`cgImage.cropping(to:)` to display-local pixel coords. See
`RegionCaptureController.captureWithScreenCaptureKit(quartzRect:logicalSize:)`
for the full pattern (bridges `SCShareableContent.excludingDesktopWindows` async
plus `SCScreenshotManager` callback into a synchronous call via `Task.detached`,
`withCheckedThrowingContinuation`, and `DispatchSemaphore` — safe because the
completion fires on a background queue, never main).

## System Junk Cleaner

Menu → Maintenance → "Clean System Junk…" (`AppAction.cleanSystemJunk`) opens
`JunkCleanerView` (SwiftUI, hosted by `JunkCleanerController`). What counts as
junk and what is never touched lives in `SnappyCore/JunkCleaning.swift`
(`JunkCategory` roots/strategy/age limits, `JunkSafety` containment, protected
names, running-app checks) and is unit tested. `JunkScanner` does the file I/O
off the main thread and re-runs `JunkSafety.canRemove` on every item right
before removing it. Default is move-to-Trash (recoverable); categories are
limited to caches/logs/temp/build products — never Documents, Preferences,
Application Support or Containers. Add new categories in `JunkCategory` only.
Selection is a tree (`SnappyCore/JunkTree.swift`, `JunkNode`): each scanned
top-level folder is a node whose children are listed lazily as the user
unfolds them (`JunkScanner.loadChildren`); checkboxes are tri-state and
`removalTargets()` resolves ticks into the highest fully-ticked `.whole`
nodes. `.contents` nodes (app cache folders, folders grouping old log/temp
files) are never removed themselves — only what's inside them.

## Mac Health

Menu → Maintenance → "Mac Health" (`AppAction.toggleMacHealth`, optional
shortcut) opens a standard titled `NSWindow` (`MacHealthController`/`MacHealthView`;
position autosaved as "QuickPanel" and shortcut raw name "quickPanel", both kept
from before the rename)
with disk, memory pressure, battery, CPU, network rates and external drives.
`SystemMonitor` samples every 2 s only while the panel is open (stopped in
`windowWillClose`). Math/wording is pure in `SnappyCore/SystemMetrics.swift`
(tick deltas, 32-bit counter wrap, rate/battery formatting, disk levels).
Actions: Free Up → junk cleaner; Optimize → heaviest apps with Quit plus
`purge` via an admin prompt (`MemoryOptimizer`); Test Speed → Apple's
`/usr/bin/networkQuality -c`; Eject for drives. The Wi-Fi name (SSID) needs
Location access on macOS 14+ — `bundle.sh` adds `NSLocation*UsageDescription`.

## App Uninstaller

Menu → Maintenance → "Uninstall Apps…" (`AppAction.uninstallApps`) opens
`AppUninstallerView` (`AppUninstallerController`/`AppUninstallerModel`). Apps
come from /Applications and ~/Applications; Apple (`com.apple.*`) apps and
Snappy itself are refused (`AppLeftoverRules.refusal`). Which ~/Library items
belong to an app is decided in `SnappyCore/AppLeftovers.swift` and is unit
tested: exact bundle ID, the app's own embedded helpers/extensions, and the app
name (also nested as "Vendor/Name", e.g. `Google/Chrome`) are ticked; mere
bundle-ID prefixes and third-party embedded components (updaters, Sparkle) start
unticked; team-prefixed vendor data is hidden when another installed app has the
same signing team; another installed app's data (`com.foo.app.beta`) is never
claimed.
Results reuse the `JunkNode` tree and `JunkNodeRow` views (shared via
`JunkTreeModel` in `JunkTreeViews.swift`). `AppUninstaller.remove` moves items
to the Trash after `AppLeftoverRules.isRemovable`; a non-writable app bundle
falls back to Finder (Apple Events, `NSAppleEventsUsageDescription`) so macOS
can prompt for an admin password. Removal is blocked while the app runs.

## Mini Display (Jungle Leopard USB screen)

Streams a system dashboard (CPU per-core load + temp, GPU load + temp, RAM,
storage free + read/write, network, clock) to a Jungle Leopard USB mini display
(tested: 9.16" 1920x462, model `AW_F101-NOR-FL7707N-9.16inch-hor`, fw 5.3).
Status-menu section "Mini Display" (only the connection line — model + firmware —
and the "Sync" toggle that starts/stops streaming and frees the serial port) and
the Settings tab "Mini Display" (Sync/brightness/theme, the widget layout and photo
options; brightness, theme and widgets are Settings-only; Settings is a toolbar-style
`NSTabViewController` built in `StatusMenuController.showSettings(_:)`, one
`SettingsView(tab:)` per `SettingsTab`: General / Shortcuts / Mini Display / Cloud),
both driven by
`MiniDisplayController` (`@AppStorage`-style keys `miniDisplayEnabled`,
`miniDisplayBrightness`). Started from `AppDelegate`, closed on terminate.

- Protocol is pure and unit tested in `SnappyCore/MiniDisplayProtocol.swift`:
  USB CDC-ACM serial (VID 0x33C3, shows up as `/dev/cu.usbmodem*`), command
  frames `55 AA | len u16 | cmd | payload | sum16`, image frames
  `len u32 | JPEG | sum16`. JPEGs must be **baseline 4:2:0** and under
  `MiniDisplayInfo.maxJpegBytes`; ImageIO's default JPEG output qualifies.
- `MiniDisplayEngine` runs on its own thread: open port → `getInfo` (JSON) →
  `live` → render with `MiniDisplayRenderer` → send ~4 fps (a still must be
  re-sent continuously or it shows half-drawn) with `live` keep-alive every 1.5 s.
- Rotation: the firmware rotates every frame by the reported `angle`;
  pre-rotating by the same angle comes out upright (verified for angle 270).
- Brightness: `setLight` (0x03) is acknowledged but does not change the
  backlight on fw 5.3 (tested: in live, after close, after flush, after
  restart), so the renderer dims with a black overlay as well.
- Temperatures use private `IOHIDEventSystemClient` via `dlsym`
  (`MiniDisplayThermal`); M1-family only exposes PMU sensors (`tdie*` → CPU,
  `TPxg` → GPU, `NAND` → SSD).
- Layout: n columns × 2 rows of slots, one widget per slot (`SnappyCore/MiniDisplayLayout.swift`,
  `MiniDisplayWidget`: cpu, gpu, ram, storage, clock, network, topCPU, topMemory, claude,
  calendar, reminders, photo), stored as JSON in `miniDisplayLayout` and edited in
  Settings ▸ Mini Display (`SlotGridEditor`: click a slot → popover list of widgets;
  column stepper). `set(_:column:top:)` keeps the photo alone in its column.
  `placements(...)` is pure/tested: empty columns skipped, the shown columns
  share the width equally, a lone widget fills the
  column, photo takes a whole column sized by its aspect. Data sources (Photos, EventKit, Claude, process scan) run
  only for placed widgets. The old per-card switches (`miniDisplayPhotosEnabled`,
  `…TopAppsEnabled`, `…CalendarEnabled`, `…RemindersEnabled`, `…ClaudeEnabled`) are
  read once by `MiniDisplayLayout.migrated` when no layout is saved.
- Themes: `SnappyCore/MiniDisplayTheme.swift` (Midnight default, Graphite, Ocean, Forest,
  Sunset, Arctic, Amber Terminal, Paper light) — background, card tint, text, per-widget
  accents and good/warning/critical status colours; `MiniDisplayThemeTests` enforces
  WCAG contrast (text ≥ 7:1, dim text and accents ≥ 3:1) for every theme. Picked in
  Settings ▸ Mini Display (`miniDisplayTheme` = theme id); the renderer never hard-codes
  colours (calendar dots keep each calendar's own colour).
- Photos widget:
  `MiniDisplayPhotoSource` shows a random image from the chosen album
  (`miniDisplayPhotosAlbum`, "" = All Photos; Settings "Album" picker) every
  `miniDisplayPhotosInterval` s (5 s–5 min), crossfading over 1 s — the engine runs
  at 20 fps only during the fade, otherwise 4 fps — in the
  full-height card at the right of the screen, shaped by `miniDisplayPhotosAspect`
  (16:9 … 3:4, default 4:3; Settings "Frame" picker) (only photos stored on this Mac: with Optimize Mac
  Storage, PhotoKit fails on cloud-only originals — 3164 / CloudPhotoLibrary
  1005 — so those are skipped and remembered); the dashboard cards shrink into the rest. Needs
  `NSPhotoLibraryUsageDescription` plus the
  `com.apple.security.personal-information.photos-library` entitlement
  (`Resources/Snappy.entitlements`, applied by `bundle.sh` under hardened
  runtime). Launch with `open` when testing — running the binary from a
  terminal attributes the Photos prompt to the terminal and access is denied.
- Calendar / Reminders widgets: `MiniDisplayAgendaSource` reads EventKit (refresh
  every 60 s + `EKEventStoreChanged`); selection/order/labels are pure in
  `SnappyCore/AgendaFormatting.swift`. Needs the `NSCalendars*`/`NSReminders*`
  usage strings and the `com.apple.security.personal-information.calendars`
  entitlement (covers reminders too).
- Claude plan usage (mini display only, no menu section; runs only while placed,
  via the `claude` widget — one slot: Session + Weekly rows; full height: two gauges): `ClaudeLimitsMonitor`
  shows Session (5hr) / Weekly (7 day) % + reset times, like Claude Code's
  "Account & Usage" panel. It reads Claude Code's Claude.ai login from the Keychain
  (service `Claude Code-credentials`; several items share that name — one may only
  hold `mcpOAuth` — so it lists attributes first and opens the one under the macOS
  user name / most recently modified) and calls the **undocumented** endpoint
  `GET https://api.anthropic.com/api/oauth/usage` (`anthropic-beta: oauth-2025-04-20`)
  every 5 min. It never refreshes the token (that would rotate Claude Code's refresh
  token); expired → shows a note and waits for Claude Code. Account email/org come
  from `~/.claude.json` `oauthAccount`; last values per account are kept in
  `claudeLimitsByAccount` so a failed fetch still shows that account's last-known usage.
  Parsing/wording is pure in `SnappyCore/ClaudeLimits.swift`.
- Top CPU / Top Memory widgets: `MiniDisplayProcesses`
  (libproc `proc_pid_rusage`, every 2 s, only while the card is on) → top 3 by CPU
  (% of the whole machine, same scale as the CPU card — not Activity Monitor's per-core %) and by memory footprint; only apps count: NSWorkspace Dock apps +
  non-Apple menu-bar apps, each process assigned to the **outermost** running app
  bundle containing it (helpers like "Microsoft Edge Helper" register as apps too);
  daemons/kernel/CLI tools are dropped (`SnappyCore/ProcessUsage.swift`). rusage CPU times are **Mach ticks** on
  Apple Silicon — convert with `mach_timebase_info`. Names are the bundle folder names
  ("Visual Studio Code", not the process name "Code").
- CPU half shows `ProcessInfo.thermalState` (Nominal/Fair/Serious/Critical); the
  NETWORK header shows the default sound output + volume/mute (`MiniDisplayAudio`,
  CoreAudio).
- The clock card also shows the Vietnamese lunar date (`SnappyCore/LunarCalendar.swift`,
  Hồ Ngọc Đức's algorithm at UTC+7 — not Foundation's `.chinese` calendar, which is
  UTC+8 and puts Tết on a different day in e.g. 1985 and 2007).
- Only one process can own the serial port — quit any other panel app first.
- Dev: set `SNAPPY_MINIDISPLAY_DEBUG_DIR=/some/dir` to get `minidisplay.log`
  and a `preview.jpg` of the frame being sent; otherwise logs go to NSLog
  (`Snappy: MiniDisplay:`).

## Display Controls (BetterDisplay-style)

Status panel ▸ Displays column: one row per display (click pops up an NSMenu
from `DisplaysMenu`: contrast/volume/mute, Resolution, Refresh Rate, Rotation,
Mirror, Set as Main Display, Disconnect…) followed by a brightness slider; then
"Reconnect <name>" rows. Settings ▸ Displays (`DisplaySettingsView`) has the software
dimming switch and each display's control method; hotkeys (brightness/volume/mute,
no defaults) act on the display under the pointer and show `DisplayOSD`.

- Private APIs live in the ObjC target `SnappyDisplayPrivate`, all resolved at
  runtime (dlsym / NSClassFromString) — missing API ⇒ feature hidden:
  DisplayServices (Apple display brightness), IOAVService (DDC on Apple
  Silicon; Intel DDC is not implemented), CoreDisplay (`IODisplayLocation`,
  product name), `CGSConfigureDisplayEnabled`, MonitorPanel `MPDisplay`
  (rotation).
- Pure/tested in SnappyCore: `DDC.swift` (packets, reply parsing, EISA vendor,
  display ↔ I2C pairing — the framebuffer IORegistry path is decisive),
  `DisplayModes.swift` (resolution/refresh menus, main-display origins),
  `DisplayBrightness.swift` (1/16 steps, gamma dimming floor).
- DDC timing (measured on Dell U4320Q / Samsung S32B80P): every request must be
  written **twice** 10 ms apart, ~150 ms between transactions, ~60 ms before
  reading the 11-byte reply, and never to two monitors at once — `DDCChannel`
  uses one shared serial queue. `6E 80 BE` = null message (busy). Monitors
  that don't answer brightness fall back to gamma-table software dimming.
- **Disconnect safety** (a test once mirrored the main display away): never
  disable a display in a mirror set or the last active one, confirm first,
  `.forSession` only, ids persisted in `displaysDisabledBySnappy` and
  re-enabled on quit and next launch.
